# 법률·조례 수집, 청킹, 검색 및 판정 연결

이 문서는 국가법령정보센터 자료와 지자체 조례가 수집되어 인허가 판정과
Gemini 답변에 전달되는 실제 경로를 설명한다. 핵심 원칙은 **수치 판정과 근거
검색을 분리**하는 것이다.

## 전체 흐름

```text
국가법령정보센터 공동활용 API
  ├─ 현행 법령 검색(target=law) ──────────────> 현행성·원문 링크 검증
  └─ 자치법규 검색/본문(target=ordin)
       ├─ 도시·군계획 조례 XML
       │    ├─ 건폐율·용적률 정형 JSON ───────> 결정적 수치 판정
       │    └─ 조문·별표 청크 ────────────────> TF-IDF 근거 검색
       └─ 건축 조례 XML/HWP
            ├─ 대지 안의 공지 정형 JSON ──────> 결정적 이격 계산
            └─ 관련 조문 청크 ────────────────> TF-IDF 근거 검색

필지 진단
  ├─ 정형 JSON + 법적 조건식으로 판정·계산
  ├─ 관할·용도지역·건축물 용도로 관련 청크 검색
  ├─ 계산 결과·공간 중첩·근거 조문을 구조화
  └─ Gemini는 구조화 결과를 읽어 자연어로 설명
```

LLM이나 검색 청크가 건폐율·용적률·이격거리 같은 수치를 새로 만들지 않는다.
법적 수치는 정형 데이터와 코드의 조건식이 결정하며, 청크 검색은 적용된 판정의
근거 조문을 찾아 보여주는 용도다.

## 도시·군계획 조례 수집

수집기는 `backend/scripts/collect_ordinances.py`다.

1. `lawSearch.do`에 `target=ordin`, 검색어 `도시계획 조례`를 보내 전국
   자치법규 목록을 가져온다.
2. 자치법규 종류가 `조례`이고 이름이 `도시계획 조례`, `군계획 조례`로 끝나는
   본문만 남긴다. 시행규칙·세칙·특별회계 조례는 제외한다.
3. 지자체별 시행일이 가장 최신인 한 건을 선택한다.
4. `lawService.do`에서 MST별 XML 본문을 받고
   `backend/scripts/.cache_ordin/<MST>.xml`에 캐시한다.
5. 조 제목과 본문에서 국토계획법 시행령 제84조제1항·제85조제1항을 인용하는
   기본 건폐율·용적률 조문을 찾는다. 예외·특례·완화 조문은 기본값으로 쓰지 않는다.
6. 21개 표준 용도지역별 퍼센트를 추출한다. 조례에 숫자가 없으면 `null`로
   남기며 추측하지 않는다.
7. 시행령 상한을 초과한 값은 파싱 오류로 보고 폐기하거나
   `ordinances_needs_manual.json`의 검수 대상으로 분리한다.

결과 파일은 다음과 같다.

- `backend/app/data/ordinances.json`: 사람이 원문과 대조한 11개 관할
- `backend/app/data/ordinances_auto.json`: 자동수집 196개 관할
- `backend/app/data/ordinances_needs_manual.json`: 수동 확인 대상

런타임의 `backend/app/tools/ordinance.py`는 검증본을 자동수집본보다 우선한다.
조례값이 없을 때 도시지역은 법정 상한을 사용할 수 있지만, 실제 수치를 시·군
조례가 정하는 비도시지역은 조례가 없으면 판정 불가로 처리한다.

## 건축조례와 이격거리 수집

원문 수집기는 `collect_setbacks.py`, 첨부표 수집기는
`collect_setback_tables.py`다.

- `target=ordin`에서 지자체별 최신 건축 조례를 선택한다.
- `대지 안의 공지`, `인접 대지경계`, `건축선 후퇴`, `이격` 관련 조문과 별표만
  `setbacks_raw.json`에 보관한다.
- HWP 별표는 표의 병합 셀과 계층 조건을 유지해 추출한다.
- `parse_setbacks_grid.py`가 용도·용도지역·연면적 조건과 전면·인접 이격을
  `setbacks.json`의 규칙으로 만든다.
- `setback_rules.lookup()`가 `지자체 + 용도 + 용도지역 + 연면적` 조건을 순서대로
  평가한다.

현재 `setbacks.json`은 120개 지자체를 포함한다. 자동 파싱값은 표본 검수가
필요하며, 원문 검색 청크 자체를 수치 계산에 사용하지 않는다.

### 별표가 없는 관할(no_appendix)과 조문 내 이미지 표

일부 지자체(전국 44곳: 양평·가평·광주·여주 등)는 `collect_setback_tables.py`가
`no_appendix`로 표시된다 — 건축조례 '대지 안의 공지' 조문이 거리 값을 **본문·HWP
별표가 아니라 조문 안 이미지(표)로** 담고 있어 XML/HWP 수집이 못 잡기 때문이다.
이 경우 수치를 지어내지 않고, **원문 이미지(ELISIMG)를 사람이 확인해** `setbacks.json`에
`review_status: "image_manually_verified"` + `source_images`(front/adjacent URL)로
반영한다. 예: 경기도 양평군 제23조(단독주택 전용주거 1/1m, 그 밖 1/0.5m 등).

상위 근거인 「건축법 시행령」 제80조의2·[별표 2] 대지의 공지 기준(전국 공통, 범위값을
건축조례에 위임)은 `ordinance_index_chunks.json`에 원문 청크로 있으나 정형
`setback_rules`에는 아직 fallback으로 반영되지 않았다(조례 미규정 관할의 잔여 gap).

## 국가 법령 수집과 청킹

`backend/scripts/collect_land_permit_laws.py`는 국가법령정보센터 `target=law`에서
토지·개발·건축 인허가 핵심 법률·시행령·시행규칙 28개를 수집한다. 조문은
`<조문단위>`, 별표는 `<별표단위>`로 나누고 법령명·조문·시행일·원문 URL을
보관한다. 현재 수집본은 1,748청크다. 원문 청크는 설명과 근거 검색용이며
허용 여부나 수치를 직접 결정하지 않는다.

생성물 `legal_corpus_chunks.json`은 조례 청크와 함께 색인된다. 런타임은
`scope=law`와 `scope=ordinance`를 분리해 전국 법령과 선택 관할 조례가
섞이지 않게 검색한다. 통합 색인은 현재 9,333청크·어휘 35,194개다.

## 조례 조문 청킹

법률 간 적용 관계는 `legal_conflict_rules.json`을 `legal_conflicts.py`가
종합 판정 전에 평가한다. 명시적 금지, 예외 입증 필요, 독립 법률의 누적 적용을
구분하며 특별법 우선·완화·인허가 의제는 검수된 명시 규칙이 있을 때만 적용한다.

`backend/scripts/build_ordinance_index.py`가 색인을 만든다.

### 입력

- `.cache_ordin/*.xml`: 도시·군계획 조례 원문
- `ordinances_auto.json`: 관할, 조례명, 시행일, 원문 URL 메타데이터
- `setbacks_raw.json`: 건축조례 이격 관련 원문

### 선택 및 분할 규칙

- 조문은 XML의 `<조제목>`과 `<조내용>` 단위로 한 청크를 만든다.
- 별표는 `<별표내용>` 단위로 한 청크를 만든다.
- 건폐율·용적률·용도지역·높이·이격·공지·건축선·일조·경관·지구단위 등
  인허가 관련 키워드가 있는 조문만 색인한다.
- 본문은 현재 최대 1,200자로 저장한다.
- 각 청크에는 `jurisdiction`, `ordinance`, `article`, `title`, `text`,
  `effective_date`, `url`, `kind`를 저장한다.
- 청크 종류는 `도시계획조례`, `도시계획조례-별표`, `건축조례-이격`이다.

현재 실측 색인은 다음과 같다.

| 항목 | 값 |
|---|---:|
| 전체 청크 | 7,585 |
| 관할 | 193 |
| 도시계획조례 조문 | 6,988 |
| 도시계획조례 별표 | 18 |
| 건축조례 이격 | 579 |
| 어휘 | 24,382 |
| 희소행렬 비영 요소 | 1,574,857 |

### 벡터화

외부 임베딩 API나 별도 벡터DB를 사용하지 않는다.

1. 단어 토큰과 한글 2·3그램을 함께 만든다.
2. 문서빈도 2 미만 또는 전체 청크의 60%를 초과하는 토큰을 제거한다.
3. `1 + log(tf)`와 IDF를 곱한다.
4. 문서 벡터를 L2 정규화한다.
5. CSR 희소행렬을 `ordinance_index.npz`에 저장한다.

생성물:

- `ordinance_index_chunks.json`: 청크 본문과 메타데이터
- `ordinance_index_vocab.json`: 토큰과 열 번호
- `ordinance_index.npz`: IDF 및 L2 정규화 TF-IDF CSR

## 런타임 검색과 관할 격리

`backend/app/tools/ordinance_index.py::search()`가 검색한다.

- 질의는 보통 `용도지역 + 건축물 용도 + 건폐율 + 용적률 + 이격 + 대지 안의
  공지 + 건축 제한`으로 만든다.
- `jurisdiction`을 필수적으로 넘겨 다른 지자체 조례가 섞이지 않게 한다.
- `effective_on`이 있으면 그 날짜보다 뒤에 시행된 청크를 제외할 수 있다.
- 정규화 질의와 청크의 내적으로 코사인 유사도를 계산한다.
- 기본 상위 4개를 `ordinance_evidence`에 넣는다.

검색 결과에는 점수·관할·조례명·조문·제목·종류·본문 일부·시행일·원문 URL이
포함된다. 검색 결과가 없다고 법적 기준이 없는 것은 아니며, 정형 판정 결과와
원문 확인 상태를 별도로 표시한다.

### 색인 파일이 없으면 근거 섹션이 통째로 사라진다 (2026-08-26 확인)

`ordinance_index.available()`은 `ordinance_index.npz`·`_chunks.json`·`_vocab.json`
세 파일의 존재 여부다. 셋 다 `.gitignore` 대상이고(대용량, 재생성 가능) **어떤 코드나
systemd 유닛도 기동 시 재생성하지 않는다.** 따라서 클론·서버 이관 직후에는 색인이 없다.

없을 때 `prediagnosis.run_prediagnosis`는 예외 없이 조용히 빈 배열을 넣는다.

```python
if jurisdiction and ordinance_index.available():
    state["ordinance_evidence"] = ordinance_index.search(...)
else:
    state["ordinance_evidence"] = []
```

그 결과가 아래로 연쇄한다.

| 대상 | 색인 없을 때 |
|---|---|
| `ordinance_evidence` | `[]` |
| `## N. 지자체 조례 근거자료` 섹션 | 헤더 자체가 생성되지 않음 |
| 프런트 접기/펼치기 | `COLLAPSIBLE_SECTIONS` 규칙은 정상. 감쌀 섹션이 없어 안 보임 |
| `legal_evidence` 의 semantic 부분 | `[]` — 카탈로그 직접 근거만 남음 |

**화면에서는 "해당 조례가 없다"와 구분되지 않는다.** 조례 근거가 안 보인다는 신고를
받으면 데이터나 정규식보다 먼저 `ls backend/app/data/ordinance_index.npz`를 확인한다.
복구는 `scripts/build_ordinance_index.py` 한 번이다.

건폐율·용적률 수치는 `ordinances*.json`에서 오므로 색인과 무관하게 정상 표시된다.
수치는 나오는데 근거 조문만 사라지는 형태라 원인 추적이 어렵다.

## 현행 법령 검증

`backend/app/tools/law_open.py`는 진단에서 실제 사용된 근거 문자열을 읽어 법령명을
추출한다.

- 건축 가능 판정, 농지·산지 전용, 부담금, 도로·접도, 예상 인허가 단계의
  `legal_basis`와 `basis`가 입력이다.
- 국가법령정보센터 `target=law`에서 정확한 법령명을 우선 선택한다.
- 시행일·공포일·제개정구분·소관부처와 인증정보가 없는 공개 원문 URL을 반환한다.
- 최대 10개 법령을 병렬 조회한다.
- 일부 실패는 `PARTIAL`, 모두 실패는 `UNAVAILABLE`로 구분한다.

이는 법령의 현행성과 링크를 확인하는 단계다. 법령 본문 전체를 벡터 색인에 섞거나
LLM이 임의로 조문을 생성하게 하지 않는다.

## 용도지구·구역 제약 판정

`backend/app/tools/zoning.py`는 용도별 허용 판정과 함께 용도지구·구역에 걸린
심의·제한을 판정한다. 이 판정은 건폐율·용적률·이격 같은 수치를 만들지 않는다.
수치는 앞 절대로 `ordinances*.json`·`setbacks.json`과 조건식에서만 오며, 이
절은 협의·허가 경로 같은 제약 노트만 붙인다.

- 토지이용계획의 지역지구명은 조례·연도에 따라 명칭 변형이 많아 정확히
  일치시키지 않고, `_CONSTRAINT_KEYWORDS`의 키워드가 이름에 들어가면 매칭해
  `_match_constraints()`가 심의·제한 노트를 만든다.
- 매칭된 지구가 있으면 `lookup_zoning_rules()`의 허용·조건부 판정이 조건부로
  낮아지고, 검토 의견과 규제 범례에 그 협의·허가 경로가 반영된다.
- 이번 세션에서 추가한 지구·구역과 근거는 다음과 같다.
  - 역사문화환경(보존지역): 문화재보호법 제13조·국가유산기본법 — 건설공사 시
    현상변경 허가와 국가유산청(지자체) 영향검토.
  - 수질보전 특별대책지역·특별대책지역: 환경정책기본법상 특별대책지역 —
    권역별로 오수·폐수 배출과 건축·개발이 제한되며 유역환경청 협의.
  - 배출시설설치제한지역: 물환경보전법 — 폐수·오수 배출시설 설치 제한과
    오수처리계획 확인.
  - 수변구역: 한강수계 등 — 오수 배출과 건축 행위 제한.

일부 지구는 검토 용도에 따라만 제약이 된다. `_FACILITY_SCOPED`에 따라
가축사육제한구역(가축분뇨법)은 축사·축산시설에만, 교육환경보호(학교정화)구역의
금지시설 제한은 숙박·유흥 등에만 걸린다. `lookup_zoning_rules(facility=...)`가
검토 용도를 받아 해당 시설이 아니면 그 지구를 제약에서 제외한다.

## 용도구역 행위제한 축 (district_use_rules.json)

`backend/app/data/district_use_rules.json`이 **행위제한** 축을 담는다. 절차 축
(`permit_rules.json` → 어떤 허가를 밟나)과 분리된 별개 축으로, "이 구역에서 이
용도가 되나"에 답하고 그렇게 만든 조문을 함께 돌려준다.

두 종류의 구역을 같은 구조로 담는다.

| 구역 | 근거 | 판별 키 |
|---|---|---|
| 농림지역 | 국토계획법 시행령 제71조·별표 21 | 용도지역명(`zones`) |
| 자연환경보전지역 | 국토계획법 시행령 제71조·별표 22 | 용도지역명(`zones`) |
| 농업진흥구역 | 농지법 제32조제1항, 시행령 제29조 | 레이어 코드 `UEA110` |
| 농업보호구역 | 농지법 제32조제2항, 시행령 제30조 | 레이어 코드 `UEA120` |
| 임업용산지 | 산지관리법 제12조제1항 | 레이어 코드 `UFM110` |
| 공익용산지 | 산지관리법 제12조제2항 | 레이어 코드 `UFM120` |

구역명은 고시·연도에 따라 표기가 흔들리므로 **코드를 이름보다 먼저** 본다
(`district_use.districts_for()`).

판정은 **2단계**다. 적용 법령을 먼저 정하고, 그 다음에 룰셋을 돌린다.

```
resolve_governing(districts)   1단계 — 어느 법이 적용되나 (제76조제5항)
        ↓ applied / superseded / basis
evaluate(districts, …)         2단계 — 그 법의 허용행위로 판정
```

**1단계를 건너뛰면 안 된다.** 겹친다고 무조건 누적이 아니다. 국토계획법
제76조제5항제3호는 이렇게 정한다.

> ⑤ … **제1항부터 제4항까지의 규정에도 불구하고** 각 호에서 정하는 바에 따른다.
> 3. 농림지역 중 농업진흥지역, 보전산지 또는 초지인 경우에는 각각 「농지법」,
> 「산지관리법」 또는 「초지법」에서 정하는 바에 따른다.

별표 21은 제1항 위임이므로 이때 **적용되지 않는다. 누적이 아니라 대체다.**
룰셋의 `supersedes: ["농림지역"]`이 이 관계를 담는다(농업진흥구역·농업보호구역·
임업용산지·공익용산지).

그래서 농림지역 + 농업진흥구역에서 가능한 것은 별표 21의 "단독주택 1천㎡ 미만"이
아니라 농지법 제32조제1항제3호의 **농업인 주택**이다. 일반 단독주택은 농림지역
단독 판정에서는 조건부지만 농업진흥구역이 겹치면 근거가 사라져 불가가 된다.

판정 이유는 어느 법으로 판단했는지부터 밝힌다 — "농림지역이지만 농업진흥구역이므로
국토계획법 제76조제5항제3호에 따라 개별법이 적용됩니다."

- 대체가 없는 조합은 **누적 적용**하고 한 곳이라도 금지면 금지다.
- 예외 열거에 해당해도 판정은 **`conditional` 이 상한**이다. 대부분 대통령령·
  부령의 면적·자격 요건이 남아 있어 `allowed` 로 올리지 않는다.
- 열거에 없으면 `not_allowed`. 아는 구역이 없으면 `unknown` 이며 이 축은 판정을
  만들지 않는다.
- 건폐율·용적률·이격 수치는 만들지 않는다. 그건 `ordinances*.json`·`setbacks.json`
  과 결정적 조건식의 몫이다.

결과는 `regulation.district_restriction`으로 실려 나가고,
`_merge_permit_legal_evidence()`가 이 근거를 **절차 근거보다 먼저** 화면 목록에
싣는다. "왜 조건부인가"의 답(제32조)이 빠지고 "그럼 뭘 하면 되나"(제34조)만
남는 상태를 만들지 않기 위해서다.

### 건축법 용도로 매칭해도 되는 축과 안 되는 축

허용행위마다 `match` 로 구분한다.

| 축 | 열거 기준 | `match` | 매칭 |
|---|---|---|---|
| 국토계획법 시행령 별표 21·22 | **건축법 용도** — "제18호가목의 창고" | (기본) | 용도·시설명 둘 다 |
| 농지법 제32조 · 산지관리법 제12조 | **시설의 성격** — "농업인이 …건조·보관하기 위하여 설치하는 시설" | `"facility"` | 시설명만 |

**농지법 제32조에는 '창고시설'·'교육연구시설' 같은 건축법 용도가 나오지 않는다.**
시행령 제29조제4항제2호가목이 정하는 것은 "농업인 또는 농업법인이 자기가 생산한
농산물을 건조·보관하기 위하여 설치하는 시설"이다. 일반 창고시설 질문을 농업용
시설로 가정해 예외를 열면 조문에 없는 판정이 나간다.

그래서 `농업진흥구역 + 창고시설` 은 `not_allowed` 이고, `농업진흥구역 +
"농산물 건조시설"` 은 `conditional` 이다. 불가로 끝내지 않고
`narrower_paths()` 가 조문상 열리는 경로를 이유에 함께 싣는다.

### 용도별 현황표도 이 축이 만든다

`uses_for_zone(zone, land_districts)` 는 행위제한 축이 아는 구역이면 그 룰셋으로
현황표를 만든다. `building_use_rules.json` 의 간이 판정표는 국토계획법 용도지역만
알아서, 농림지역 창고시설을 **조건 없는** '조건부'로 내보내고 별표 21 이 허용하는
단독주택을 불가로 내보낸다. 그대로 LLM 에 넘기면 "창고시설이나 교육연구시설 등
예외적으로 허용되는 시설" 같은 조문에 없는 문장이 나온다.

조건부 항목은 **허용행위 이름**으로 표기한다 — `창고시설` 이 아니라
`창고(농업·임업·축산업·수산업용)`, `단독주택` 이 아니라
`단독주택(부지면적 1천㎡ 미만)`. 뭉뚱그린 용도명이 근거처럼 읽히면 안 된다.

일반 용도가 전부 불가인 구역(농업진흥구역 등)에서는 `facility_specific` 이
"그럼 뭐가 되나" 를 답하는 유일한 목록이다. 용도 미지정(`시설물`) 질문은 이
목록으로 판정한다 — `시설물` 은 내부 표식이라 행위제한 열거에 없고, `evaluate`
결과를 그대로 쓰면 통째로 불가가 된다.

### 두 축은 실제로 서로를 인용한다

별표 22 제1호가목은 자연환경보전지역의 단독주택을 "「농지법」 제32조제1항제3호에
따른 농업인 주택 및 어업인 주택"으로만 허용한다. 용도지역 축이 개별법 조문을
직접 끌어 쓰는 구조라, 두 축을 한 파일에 같은 스키마로 두는 편이 맞다.

### 하드코딩에서 옮겨온 것 (2026-08-26)

`zoning.py`에 `agricultural_house and zone == "농림지역"` 조건 분기와 산문
`reason` 문자열로 박혀 있던 판정을 이 룰셋으로 옮겼다. 그 과정에서 원문 대조로
확인된 오류가 하나 있다.

**농림지역의 일반 단독주택은 불가가 아니다.** 별표 21 제1호가목이 부지면적
1천㎡ 미만의 단독주택을 조례 없이 건축할 수 있는 건축물로 열거한다. 농업인
자격은 요건이 아니다. `building_use_rules.json`의 `단독주택`에 농림지역이
빠져 있어 불가로 떨어졌고, 농업인 주택만 분기로 되살리고 있었다.

## 지구단위계획 원문 수집·정제·청킹 (2026-08-26 신설)

3단계다. 각 단계 산출은 다음 단계의 입력이다.

```
collect_district_plans.py        고시 페이지 -> data/source/district_plans/<시군구>/<계획명>/
parse_district_plan_documents.py 원문 -> data/processed/district_plans/**/*.json (페이지·표 단위)
build_district_plan_chunks.py    정제본 -> app/data/district_plan_chunks.json
build_ordinance_index.py         조례·법령과 같은 TF-IDF 색인에 합친다
```

`data/source/`·`data/processed/` 는 `.gitignore` 대상이다(원본 156MB). 청크
JSON만 저장소에 들어가며, 원본은 위 명령으로 재생성한다.

### 수집에서 걸리는 것

| 원본 | 방식 | 함정 |
|---|---|---|
| 토지이음(eum.go.kr) | 폼 POST `FileDownload.do` | **`gosi=Y` 히든 필드와 euc-kr 인코딩이 둘 다 맞아야 한다.** 하나라도 틀리면 HTTP 200 에 "첨부파일이 없습니다" 스크립트가 와서 빈 고시와 구분되지 않는다 |
| 아산시 CMS | `download.php?...&uid=` | 링크에 확장자가 없다. 확장자로만 긁으면 본문과 무관한 사이드바 문서를 가져온다. 파일명은 앞의 `preview.php?file_nm=` 에 있다 |
| 지자체 CMS 일반 | 직접 GET | 비브라우저 User-Agent 에 응답 없이 연결을 끊는 곳이 있다. 브라우저 UA + Referer + 재시도 |

받은 바이트는 매직 넘버로 검사한다. 실패해도 200 에 HTML 경고문을 주는 사이트가
있어 크기·헤더만으로는 성공을 판단할 수 없다.

### 정제에서 걸리는 것

- **HWP 는 `pyhwp` 가 필요하다**(`hwp5txt`·`hwp5html`). `six` 도 함께 있어야
  임포트된다. 둘 다 `requirements.txt` 에 있다.
- `hwp5html` 은 문서 전체를 HTML 로 변환하므로 큰 시행지침에서 3분을 넘긴다.
  표 추출은 180초 타임아웃 후 포기하고 본문만 살린다. 한 문서가 배치를 막지 않게
  파일 단위 예외도 잡는다.
- **표를 반드시 함께 청킹한다.** 획지별 건폐율·용적률·최고층수는 대부분 표에만
  있고 `hwp5txt` 본문에는 `<표>` 표시만 남는다. 아산 탕정 결정조서는 본문 864자,
  표 68,545자다. 표를 빼면 핵심 수치가 통째로 색인에서 빠진다.
- 스캔 PDF 는 `--ocr` 로 비전 모델을 태운다. 도면 한 장에 글자가 많아 응답이
  느리므로 타임아웃 300초·재시도 2회이며, 실패한 페이지는 `OCR_FAILED` 로 남기고
  나머지 페이지 결과는 그대로 쓴다.

### source_page 가 없는 지자체는 고시 목록에서 찾는다

`collect_district_plans.py --discover 경산시 계양구 예산군` 이 토지이음 고시
목록(`gvGosiList.jsp`)을 훑어 그 지자체의 지구단위계획 결정고시를 찾아
`district_plan_sources.json` 에 `discovered: true` 로 등록한 뒤 수집한다.
이름을 주지 않으면 `sources` 가 비어 있는 지자체를 전부 대상으로 한다.

- 질의 문자열은 **euc-kr 로 인코딩**한다. UTF-8 이면 0건이 나온다.
- 제목에 `지구단위계획` 이 있어도 `열람·공고·폐지·실효·취소` 는 제외한다.
  계획 자체가 아니라 절차 고시라 원문에 계획 내용이 없다.
- 계획명은 제목 괄호 안의 `…지구단위계획` 을 쓴다.

### OCR 은 문서형만 태운다

스캔본 24건 중 파일명이 `도면·결정도·종합도·총괄도·계획도·지형도` 인 14건
(29페이지)은 지도라 텍스트 회수율이 낮고 페이지당 수 분이 걸린다. 실제로 도면을
포함해 돌렸더니 52페이지에 20분 넘게 한 건도 끝나지 않았다. 문서형 10건(24페이지)
만 태우면 몇 분에 끝난다. 도면의 획지 수치는 결정조서·시행지침 표에서 온다.

## 근거 카탈로그의 두 축 (legal_rule_catalog.json)

`legal_rule_catalog.json`은 법령 목록이 아니라 **규칙 ↔ 법령 연결표**다. 생성
스크립트가 없는 수작업 파일이므로 규칙을 추가할 때 참조도 함께 넣어야 한다.

**절차 축** — `permit_rules.json`의 룰 7개가 연결한다.

| rule_id | 연결된 조문 |
|---|---|
| `permit.demolition` | 건축물관리법 |
| `permit.farmland_conversion` | 농지법 제34조 |
| `permit.forest_conversion` | 산지관리법 제14조, 시행규칙 |
| `permit.road_review` | 건축법 제2조제1항제11호, 제44조 |
| `permit.special_review` | — |
| `permit.development_activity` | 국토계획법 제56조 |
| `permit.building_permission` | 건축법 제11조, 제14조 |

**행위제한 축** — `district_use_rules.json`의 구역이 연결한다(2026-08-26 신설).

| 구역 | 연결된 조문 |
|---|---|
| 농업진흥구역 | 농지법 제32조, 시행령 제29조 |
| 농업보호구역 | 농지법 제32조, 시행령 제30조 |
| 임업용산지·공익용산지 | 산지관리법 제12조 |
| 농림지역 | 국토계획법 시행령 제71조, 별표 21 |
| 자연환경보전지역 | 국토계획법 시행령 제71조, 별표 22 |

두 축은 목적이 다르다. 절차 축은 "그럼 뭘 하면 되나"(제34조 전용허가), 행위제한
축은 "왜 되나·왜 안 되나"(제32조 허용행위 열거)에 답한다. 화면 근거 목록은
행위제한 근거를 **먼저** 싣는다 — 판정을 만든 조문이 근거에서 빠지면 안 된다.

### RAG 질의의 순환을 끊어 둘 것

전국 법령 검색 질의는 정형 규칙이 선택한 근거에서 만들어진다. 절차 단계만 넣으면
순환이 생긴다 — 카탈로그에 없는 조문은 질의에 안 들어가고, 질의에 없으니 검색되지
않고, 그래서 계속 카탈로그 밖에 남는다. 2026-08-26 이전에 농지법 제32조가 corpus에
있는데도 근거에 한 번도 안 뜨던 원인이 이것이다.

지금은 `run_prediagnosis`가 행위제한 축이 판정한 구역명·조문도 질의에 넣는다.
행위제한 규칙을 추가할 때 이 질의 구성도 함께 확인한다.

## Gemini에 전달되는 구조

Gemini에는 원문 데이터 전체가 아니라 현재 PNU에 해당하는 구조화 진단을 전달한다.

- 용도지역·지구·지목·면적
- 용도 허용 판정과 건폐율·용적률 출처
- 농지·산지·재해·생태 공간 중첩과 면적 비율
- 도로 접도, 이격, 주차, 부담금 참고값
- 예상 인허가 단계와 법령 근거
- `legal_sources`: 현행 법령 검증 결과
- `ordinance_evidence`: 관할 조례 검색 결과
- PNU별 이전 질문·답변과 현재 검토 용도

Gemini의 역할은 이 데이터를 질문 의도에 맞게 설명하는 것이다. 판정표 수치나
공간 중첩을 일반론으로 대체하거나, 데이터에 없는 규제·법적 충돌을 만들어서는
안 된다.
